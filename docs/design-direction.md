# RaiRap — Design Direction

คู่กับ `design-spec-expense-tracker.md` (= brief) และ `development-plan.md` (= แผนงาน)

เอกสารนี้ทำสองอย่าง: **(ก)** เติม axis ที่ brief ปล่อยว่าง ด้วยการตัดสินใจที่ผูกกับเรื่องนี้โดยเฉพาะ **(ข)** ชี้จุดที่ brief ขัดกันเอง พร้อมวิธีคลี่

**กติกา:** brief ชนะเสมอ. §3 palette, §4 ฟอนต์, §6 signature, §7 blur 20px / radius 24px — ทำตามตรง ๆ ไม่แก้ตามใจ. ที่แก้ในเอกสารนี้มีเฉพาะจุดที่ brief สั่งขัดกันเอง และต้องเลือกข้างเดียว

## A. Type — Space Grotesk ไม่มีภาษาไทย

ตรวจจาก Google Fonts metadata:

| Family | subset ไทย | weights |
|---|---|---|
| Space Grotesk | **ไม่มี** | 300–700 |
| IBM Plex Sans Thai | **มี** (+ latin) | 100–700 |
| IBM Plex Mono | ไม่มี | 100–700 |

**ปัญหา:** brief §4 กำหนด `Heading = Space Grotesk 500, 20–28px` แต่หัวข้อในแอปนี้เป็นไทยแทบทั้งหมด ("งบเดือนนี้", "รายการล่าสุด"). Space Grotesk ไม่มี glyph ไทย → เบราว์เซอร์ fallback เฉพาะตัวไทย ส่วน Latin/ตัวเลขยังเป็น Grotesk → หัวข้อผสมอย่าง "งบเดือน July" ออกมาเป็นสองฟอนต์คนละตัวในบรรทัดเดียว

**คลี่:** ให้ Space Grotesk เลิกเป็น "ฟอนต์หัวข้อ" แล้วเป็น **"เสียงของเงิน"** แทน — ใช้กับตัวเลขจำนวนเงินและ Latin เท่านั้น

| Role | Family | Spec |
|---|---|---|
| Hero money | Space Grotesk 600 | `tabular-nums`, 40–56px — Latin/ตัวเลขล้วน ไม่มีไทยปน |
| Heading (ไทย) | IBM Plex Sans Thai 600 | 20–28px |
| Body | IBM Plex Sans Thai 400 | 15–16px, **`line-height: 1.65`** |
| Tabular money | IBM Plex Mono 400 | ยอดในลิสต์/ตาราง |

ข้อดีที่ได้แถม: Grotesk ถูกสงวนไว้ให้ตัวเลขเงินอย่างเดียว → กลายเป็นของเฉพาะตัวมากกว่าตอนเป็นฟอนต์หัวข้อทั่วไป. และ IBM Plex Sans Thai มี latin subset ในตัว หัวข้อผสม "งบเดือน July" จึงออกมาฟอนต์เดียวไร้รอยต่อ

**รายละเอียดภาษาไทยที่ brief ไม่ได้ครอบ:**

1. `line-height: 1.65` ขั้นต่ำสำหรับ body — ไทยมีสระบน + วรรณยุกต์ซ้อนสองชั้น (เช่น "ที่", "ปั๊ม"). ค่า 1.5 ที่จูนมาสำหรับ Latin จะทำให้วรรณยุกต์ชนบรรทัดบน
2. **ห้าม `letter-spacing` กับข้อความไทย** — ไทยเป็น cluster script การถ่างตัวอักษรจะแยกสระออกจากพยัญชนะ. ใช้ tracking ได้เฉพาะ Latin/ตัวเลข
3. **`<html lang>` ต้องตรงกับภาษาที่เลือก** — เมื่อเป็น `th` Chrome/Safari จึงใช้ dictionary line-breaking ภาษาไทย และ screen reader ต้องอาศัยค่านี้เพื่อออกเสียงทั้งไทย/อังกฤษให้ถูกต้อง

## B. Color — `--text-muted` ตกเกณฑ์ที่ brief ตั้งเอง

brief §8 สั่ง "contrast ต้องผ่าน WCAG AA" แต่ token §3 ทำไม่ได้ตามนั้นทุกที่. คำนวณจริง (`--text-muted #5C7086`, body 15px → เกณฑ์ AA = 4.5:1):

| พื้นหลัง | Contrast | ผล |
|---|---|---|
| บนกระจก `.55 white` เหนือ gradient บน | 4.66:1 | ผ่านแบบเฉียด |
| บน `--bg-gradient-top #EAF4FC` ตรง ๆ | 4.58:1 | ผ่านแบบเฉียด |
| **บน `--bg-gradient-bottom #D6EAF9` ตรง ๆ** | **4.13:1** | **ตก** |

margin เหลือ 0.16 บนกระจก แล้ว `saturate(160%)` (§7) ยังดันพื้นหลังให้เข้มขึ้นอีกนิด → กินส่วนต่างที่เหลือ

**ตัดสินแล้ว:** `--text-muted` `#5C7086` → **`#4F6379`** (เข้มขึ้น 2 สเต็ป โทนเดิม) — เป็น token เดียวที่ค่าต่างจาก brief §3

| พื้นหลัง | เดิม | ใหม่ |
|---|---|---|
| บนกระจก | 4.66 | **5.64** |
| gradient บน | 4.58 | **5.35** |
| gradient ล่าง | 4.13 ✗ | **5.00** |

นี่ไม่ใช่การขัด brief — เป็นการเลือก §8 (AA) เหนือ §3 (ค่า hex) ตอนที่สองข้อสั่งสวนกัน ต้องเลือกข้างเดียว

**Token ที่ brief ปล่อยว่าง — เติมดังนี้:**

| เรื่อง | ตัดสิน | เหตุผล |
|---|---|---|
| สีหมวดหมู่ใน pie chart | ไล่เฉดสีเดียว `--accent-deep` → `--accent-primary` → tint อ่อน **เรียงตามยอด** | §7 ห้ามกราฟหลายสี. sequential ramp บน categorical ปกติผิดหลัก เพราะสื่อว่ามีลำดับ — แต่ที่นี่ slice **เรียงตามยอดจริง** ลำดับจึงมีอยู่จริง หมวดจ่ายเยอะสุด = เข้มสุด. ข้อจำกัดกลายเป็นฟีเจอร์ |
| ไล่เฉดยังไง | interpolate ใน **OKLCH** ไม่ใช่ hex lerp | lerp ใน sRGB ผ่านโซนน้ำเงินจะออกม่วงหม่นกลางทาง |
| รายรับ vs รายจ่าย | รายรับ `--accent-mint` / รายจ่าย `--accent-primary` | ห้ามใช้แดง (§3). mint = "ดี" อยู่แล้ว. รายจ่ายไม่ใช่เรื่องแย่ จึงไม่ควรได้สีเตือน |
| `--accent-warn` เป็นตัวอักษร | **ห้าม** — ใช้เป็นพื้น/แท่งเท่านั้น | `#F5A97F` บนกระจก ≈ 1.9:1 อ่านไม่ออก. ข้อความเตือนใช้ `--text-primary` |
| กระจกซ้อนกระจก | ห้าม nested `backdrop-filter` | blur ซ้อน blur = เละ + scroll กระตุกบน Safari |

## C. Layout — dashboard โชว์เฉพาะหมวดที่ต้องสนใจ

brief §5 วาด ASCII เป็น hero → การ์ดงบ 3 ใบ → กราฟ. แต่ §1 เขียนด้วยคำว่า **"ล้อมรอบด้วยการ์ดกระจกเล็กที่แสดงหมวดหมู่ที่ใช้เกิน"**

ร้อยแก้วใน §1 บอกอะไรที่ ASCII ไม่ได้บอก: การ์ดเล็กไม่ได้แปลว่า "งบทุกหมวด" — แต่คือ **หมวดที่ใช้เกิน**

**ตัดสิน:** dashboard แสดงเฉพาะหมวดที่ `status IN ('warn','over')` (≥80%). งบครบทุกหมวดอยู่ที่ `/budgets`

- โครงหน้าเข้ารหัสข้อมูลจริง: การ์ดโผล่ = มีเรื่องต้องดู. ไม่มีการ์ด = สบายดี
- ไม่ต้องเดาว่าจะโชว์ 3 ใบไหน ถ้ามี 8 หมวด — จำนวนการ์ดมาจากข้อมูล ไม่ใช่จากกริด
- สวนทางกับ default ของ dashboard ทั่วไปที่เทสถิติทุกอย่างลงหน้าแรก
- **เคสว่าง (ไม่มีหมวดไหนเกิน 80%):** ไม่ใช่ error ไม่ใช่ empty state — เป็นข่าวดี. การ์ดใบเดียว น้ำเสียงเรียบ: "ทุกหมวดยังอยู่ในงบ" + ลิงก์ไปดูงบทั้งหมด

### Navigation — งานหลักอยู่บนแถบ งานจัดการอยู่ในโปรไฟล์

แถบหลักมี 3 ปลายทางที่ใช้บ่อยและเข้าใจง่าย: **ภาพรวม · รายการ · โปรไฟล์**

งบ, เป้าหมาย, วิเคราะห์, รายงาน, บัญชีและกระเป๋าเงิน, รายการเกิดซ้ำ, หมวดหมู่,
ตั้งค่า และออกจากระบบอยู่ที่หน้าโปรไฟล์ เพื่อลดตัวเลือกบน navigation ให้เหลือเฉพาะจุดตั้งต้น

- ทุกหน้าถึงได้ไม่เกิน 2 คลิกจากแถบหลัก
- ชื่อผู้ใช้เป็นทางเข้าหน้าโปรไฟล์; จอแคบย่อเหลือไอคอนเพื่อคืนพื้นที่ให้เมนูหลัก
- หน้ารองทั้งหมดทำให้ปุ่มโปรไฟล์มีสถานะ active ผู้ใช้จึงยังรู้ว่าตัวเองอยู่ในกลุ่มไหน
- ห้ามเติมฟีเจอร์ใหม่ลงแถบหลักโดยอัตโนมัติ ให้เริ่มจากหน้าโปรไฟล์ก่อน แล้วเลื่อนขึ้น
  เป็นเมนูหลักเฉพาะเมื่อเป็นงานที่ผู้ใช้ส่วนใหญ่ต้องสลับใช้ระหว่างวัน

### Mobile system — ไม่ใช่ desktop ที่ย่อส่วน

ที่ความกว้างต่ำกว่า 640px แยก navigation เป็นสองชั้น: utility bar ด้านบนมี RaiRap,
และการแจ้งเตือน; ส่วน 3 ปลายทางหลักอยู่ใน bottom tab bar แบบไอคอน + ข้อความ
ทุกแท็บกว้างเท่ากันและไม่ต้องเลื่อนแนวนอน

- touch target ขั้นต่ำ **44×44px**; bottom tab สูงอย่างน้อย 56px
- gutter หน้าจอ 16px, card padding 16px; ตั้งแต่ 640px ใช้ card padding 24px
- input/select/textarea บนมือถืออย่างน้อย 16px เพื่อไม่ให้ iOS Safari ซูมเอง
- bottom bar และ content padding ต้องรวม `env(safe-area-inset-bottom)`; top utility bar รวม
  `env(safe-area-inset-top)` สำหรับจอมี notch
- active state ใช้ทั้งพื้นทึบ + `aria-current`; ไอคอนอย่างเดียวห้ามใช้ ต้องมี label ตามภาษาที่เลือกเสมอ
- viewport ใช้ `viewport-fit=cover` แต่ห้ามปิด pinch-to-zoom
- breakpoint 640px ขึ้นไปกลับไปใช้ top navigation แบบ desktop เพียงชุดเดียว
- หน้าที่มี primary create action เพียงหนึ่งอย่างใช้ FAB แบบไอคอน + label ได้ โดยต้องลอยเหนือ
  bottom tab และ safe area เสมอ; ฟอร์มเพิ่มข้อมูลเปิดเป็น bottom sheet โดยไม่ดันรายการเดิม
  และเมื่อเปิดฟอร์มแล้วให้ซ่อน FAB เพื่อลด action ซ้ำบนจอ

### Transaction explorer — เวลาเป็นตัวกรองหลัก

หน้ารายการเปิดที่เดือนปัจจุบัน เพราะเป็นช่วงที่ผู้ใช้ตรวจเงินบ่อยที่สุด แถบหลักแสดงเพียง
ช่วงที่เลือก, ก่อนหน้า/ถัดไป, มุมมอง และปุ่มตัวกรอง เพื่อคืนพื้นที่แนวตั้งให้รายการ

- มุมมองมี 2 แบบ: รายการสำหรับค้นหา/แก้ไข และปฏิทินสำหรับเห็นจังหวะการใช้เงิน
- กดช่วงเวลาเพื่อเลือก **วัน · สัปดาห์ · เดือน · ปี · ช่วงกำหนดเอง**; มือถือเปิดเป็น
  bottom sheet สูงไม่เกิน 80dvh ส่วน desktop เป็น popover ที่ไม่ดันรายการลง
- ประเภท, หมวดหมู่, บัญชี, คำในบันทึก และช่วงจำนวนเงินอยู่ในปุ่ม “ตัวกรอง” พร้อม badge
  จำนวนเงื่อนไข; เมื่อใช้งานแล้วสรุปไม่เกิน 2 รายการและ `+n` ในบรรทัดเดียว
- ปฏิทินสัปดาห์/เดือนสรุปยอดต่อวัน; ปฏิทินปีสรุปต่อเดือน และเลือกเพื่อ drill down ได้
- ตัวเลขรายรับใช้เขียวอมฟ้า ตัวเลขรายจ่ายใช้ส้ม และคงเครื่องหมาย `+ / −` เสมอ
  เพื่อไม่ใช้สีเป็นข้อมูลเพียงอย่างเดียว; token ทั้ง light/dark ต้องผ่าน WCAG AA
- ยอดในปฏิทินรวมใน Postgres ด้วย `numeric(12,2)` และฟังก์ชันต้องเป็น
  `security invoker` เพื่อคง RLS; JavaScript มีหน้าที่จัดวางช่องปฏิทินเท่านั้น
- URL เก็บ view, scope, anchor และตัวกรองทั้งหมด เพื่อให้ย้อนกลับหรือแชร์สถานะเดิมได้

## D. Signature — Liquid Light Sweep

**ตัดสินแล้ว: ทำตาม brief §6 ตรง ๆ.** hero card ใบเดียว ที่อื่นห้ามมี

> *เคยพิจารณาแล้วไม่เอา — Waterline:* hero เป็นภาชนะแก้ว ระดับน้ำ = คงเหลือ÷รายรับ + ขีดบอกจังหวะตามวันที่ ดึง burn rate (§2.3) ขึ้นมาเป็น hero. แรงกว่าเพราะเข้ารหัสข้อมูลแทนที่จะประดับ แต่ **ไม่เลือก** — §6 pin sweep ไว้ชัด และ brief ชนะ. เก็บไว้เป็นทางเลือกถ้าอนาคตอยากรื้อ hero (ถ้าเอา waterline ต้องถอด sweep ออก — ของเหลวสองชั้นบนการ์ดใบเดียว = เละ)

CSS ใน §6 เป็นโครงตั้งต้น ยังขาดของจำเป็น. ตัวเต็ม:

```css
.hero-card {
  position: relative;
  overflow: hidden;          /* กันแสงล้นขอบ 24px */
  isolation: isolate;        /* ตรึง stacking context ไม่ให้ ::before ทะลุไปทับการ์ดใบอื่น */
}

.hero-card::before {
  content: '';
  position: absolute;
  inset: -50%;               /* เผื่อให้แถบเฉียง 115deg กวาดพ้นมุมการ์ด */
  pointer-events: none;
  background: linear-gradient(115deg,
    transparent 30%, rgba(255,255,255,0.4) 50%, transparent 70%);
  will-change: transform;    /* ดันขึ้น layer ของตัวเอง — ดูหมายเหตุ perf */
  animation: sweep 6s ease-in-out infinite;
}

@keyframes sweep {
  from { transform: translateX(-60%); }
  to   { transform: translateX(60%); }
}

@media (prefers-reduced-motion: reduce) {
  .hero-card::before { animation: none; }   /* §8 */
}
```

**สำคัญ — animate `transform` เท่านั้น ห้าม `background-position`.** `background-position` สั่ง paint ใหม่ทุกเฟรม บนการ์ดที่มี `backdrop-filter: blur(20px)` อยู่แล้ว = บังคับให้เบราว์เซอร์คำนวณ blur ซ้ำ 60 ครั้ง/วินาที → คือเคสกระตุกที่ระบุไว้ใน `development-plan.md` §7 เป๊ะ ๆ. `transform` + `will-change` ดัน pseudo-element ขึ้นเป็น compositor layer แยก ลอยเหนือชั้น blur → blur คำนวณครั้งเดียว

**ต้องวัดจริง:** เปิด DevTools > Rendering > Paint flashing บน Safari/iOS. ถ้า hero กะพริบตอน sweep วิ่ง แปลว่า blur ถูกคำนวณซ้ำ — layer ไม่ได้แยก

## E. Motion — เงียบไว้

brief pin ไว้แค่ signature. ที่เหลือตัดสินดังนี้:

- **Page load:** fade + ขยับขึ้น 2px, stagger 40ms ต่อการ์ด. จบใน 300ms. แค่นั้น
- **ไม่มี** scroll-triggered reveal, ไม่มี parallax, ไม่มี hover ที่การ์ดลอย — signature ทำหน้าที่ของมันแล้ว ที่เหลือต้องเงียบ
- `prefers-reduced-motion`: หยุดคลื่น/sweep, เหลือ fade ล้วน (§8)
- ตัวเลขเงินเปลี่ยนค่า: **ไม่ต้อง count-up animation** — คนมาอ่านยอดเงิน ไม่ได้มาดูโชว์

## F. Copy

brief §9 วางน้ำเสียงไว้ถูกแล้ว (บอกตรง ๆ ไม่ตำหนิ). เพิ่มกฎ:

- **คำกริยาเดียวตลอด flow** — ปุ่ม "บันทึก" → toast "บันทึกแล้ว" (ไม่ใช่ "สำเร็จ" / "เรียบร้อย")
- **ตั้งชื่อตามสิ่งที่ผู้ใช้คุม** ไม่ใช่ตามที่ระบบสร้าง — "หมวดหมู่" ไม่ใช่ "category record"
- **ตัดคำเติม** — brief §9 เขียน "เริ่มบันทึกรายการแรกกันเลย" → **"เริ่มบันทึกรายการแรก"**. "กันเลย" ไม่ได้ทำงานอะไร
- **error ไม่ขอโทษ และไม่กำกวม** — บอกว่าเกิดอะไรกับบอกวิธีแก้. §9 ทำถูกแล้ว: "หมวดเดินทางใช้เกินงบที่ตั้งไว้ 100 บาท" + ทางเลือก
- **หน้าจอว่างคือคำเชิญให้ลงมือ** ไม่ใช่ที่ระบายอารมณ์
